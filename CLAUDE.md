# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Castle Game: a procedural voxel world and colony game in **Ada 2022 + OpenGL 4.5** (GLFW). The world is 2048 x 2048 x 256 m in 0.25 m blocks. Every document a session reads is in this repo.

Read, in this order, before starting work:

1. `docs/production/State.md`: one page, rewritten at every close: where the project stands, what is next, what is on hold, where John's open calls are.
2. This file, and from `docs/conventions/` the file of each part of the game the work touches (the table at the end of this file).
3. The newest file in `docs/handoffs/`: what the last session changed and what comes next.
4. `docs/production/Production_Framework.md`: the pillars, the architecture rules, the phases, how a stage is run. `docs/production/Production_plan.md` and `Stage_log.md` are the record of what was built when and on whose word: looked things up in, not read through.
5. `README.md` (the project and the systems map), then only the `docs/systems/*.md` files the work touches.
6. From `docs/design/`: `detailed_mechanics.json` is John's design of the colony, its people and its economy (his: nothing in it is changed); `Mechanics_crosswalk.md` sets it beside the build, section by section. Read the crosswalk's section before designing anything the document covers. The older files there are the sources the document was drawn from.

`docs/` is the only copy of these documents (the old `CASTLE_GAME/DOCUMENTATION/` folder is gone; John keeps a backup). Zips and demo videos go to `CASTLE_GAME/releases/`, papers to `CASTLE_GAME/papers/`, both outside git.

## Build

```sh
gprbuild -P castle.gpr -XCASTLE_MODE=release -j0   # -> bin/
gprbuild -P castle.gpr -XCASTLE_MODE=debug -j0     # -> bin/debug/  (range/overflow/validity checks, assertions)
```

- The scenario variable is `CASTLE_MODE`, not `Mode`.
- Debug and release use separate `obj/` and `bin/` directories.
- Warnings are on (`-gnatwa`). Only 6 known warnings remain, unused formals in `tools/water_sim_check.adb`. Don't add new ones (a constant function a check hands the water goes between `pragma Warnings (Off/On, "formal parameter * is not referenced")`).
- Every executable must be listed in `for Main use (...)` in `castle.gpr`. If one needs GL or GLFW, add its linker switches there too.
- **`-ffp-contract=off` is required.** World generation must give the same world bit for bit for the same seed on every machine. Don't add FMA, fast-math, or anything that makes floats depend on the build.

## Tests

There is no test framework. Each check is its own executable in `tools/`. Run the checks in **debug**. Each one exits non-zero on failure.

**The gate** is all of what follows, from a clean copy of a commit: `tools/gate.sh [COMMIT [DIR]]` (both builds from nothing with no new warning, the nine checks in debug, the reference check, the game as it is played against its kept log, the three site scripts in release and in debug, the herds' places, the stress runner, the flora hash; three quarters of an hour: start it in the background). It leaves with 1 if any part failed and keeps every log in DIR. Nothing is reported to John as done before its gate has passed.

## Measuring: use the runner

`./bin/colony_run` runs the colony on the real world with no window, deterministically (`docs/systems/colony.md`, "colony_run"). Take every measurement and phase gate there, not in the game: a `--frames` run in the game follows real frame time and never repeats exactly. To compare a run with one loaded from a save, take the save on a rebuild: a run whose length is a multiple of 30 colony seconds (`Rebuild_S`; 1/48 of a game day, so `--days 0.0625` and not `--days 0.06`). The runner's rebuilds of edited stacks are counted from the start of each run, so a save taken between two of them loads into a run that knows of its edited ground a little sooner, and the two part a day or so later; the colony's save itself is exact (found and proved 2026-11-11; `colony_run --save` says when a save is not on a rebuild). `tools/reference_run.sh [DAYS]` is the reference run (seed 1, stake 1178 1078, camp 1172 1082, two gatherers, a forester, two hunters, a cook). The colony's command-line options, setup and log lines are in `Castle.Scenario`, shared by the game and the runner: add a new colony option there, once.

## Running headless

On this machine (Garuda, Sway, RX 6900 XT) GLFW goes to Wayland whenever `WAYLAND_DISPLAY` is set, so `xvfb-run` still opens a real window on the user's desktop, on the real GPU. Run the game directly with `--float`: the window can't be resized, so Sway floats it at exactly `--size` instead of tiling it (frames are then the size asked for). For a truly hidden window use `env -u WAYLAND_DISPLAY xvfb-run ...` (software GL: 0.2-0.7 s a frame, so `--frames N` / `--record` runs take minutes; start them in the background).

```sh
./bin/castle_game --float --size 640 360 --view 48 \
         --at X Y --cam YAW PITCH DIST --frames N --shot out.png --novsync
```

Scripted runs (`--frames`, `--record`) ignore the keyboard and mouse: a test window that takes the focus on the user's desktop used to get keys meant for something else (Space pauses the colony), which looked like an intermittent "colony never advances" stall. `--pointer "FRAME:COMMAND, ..."` drives the cursor in such a run (`move X Y`, `rel DX DY`, `member I`, `deer K`, `ground X Y`, `click`, `rclick`, `wheel N`, `esc`; frames count from the first with a colony on loaded ground; `docs/systems/interface.md`, "A scripted pointer"). It is the only way a shot or a recording can show a tooltip or a menu: `tools/demo_stage5a.sh` is a worked example. A menu opens where it is clicked and stays there while its person walks on, so aim at its rows with `rel` on the frame after the click (`150:rclick, 151:rel 96 86`), before the pointer has followed the person away. Nothing of the pointer's real-input path (`Castle.Input`: the right button let go without a drag, the held button on a scroll bar, the wheel, a key) can be exercised headless: say so, once, when a change touches it. John tries every build himself (2026-11-10: "I tested it mouse pointer and clicks work with a real mouse. I always test all your builds"), so there is no need to ask him to.

`--record DIR N` writes uncompressed PNGs of the full framebuffer (about 2.5 MB a frame even at `--size 640 360`): a few thousand frames fill `/tmp`. Make the contact sheet with ffmpeg and delete the frames straight after.

The game has many scripted options for reproducing a scenario without input: `--dig`, `--fill`, `--late`, `--puddle`, `--walk`, `--lineup`, `--stake`, `--path`, `--stockpile`, `--housing`, `--housing-inside`, `--homes-built`, `--pace`, `--no-cook-hold`, `--no-curing`, `--cart-salt`, `--no-ladders`, `--no-path-holes`, `--no-cart-pull`, `--no-cloth`, `--no-cloak-fit`, `--no-form`, `--no-reference-body`, `--no-head-shape`, `--no-rest-arms`, `--no-voxel`, `--no-chest-hands`, `--no-whole-back`, `--deer-stats`, `--no-reach-out`, `--no-zigzag`, `--no-paths-meet`, `--no-door-meet`, `--no-kill-home`, `--no-place-level`, `--no-cart-room`, `--no-full-truss`, `--no-build-help`, `--no-step-at-edge`, `--pile-flat`, `--no-steep-refuse`, `--no-cutaway`, `--all-roofs`, `--gatherers`, `--speed`, `--record DIR N`, `--pan DX DY` (`--pan-back`), `--save`, `--load`, `--hud`, `--mouse`. See the main README and `docs/systems/colony.md` for the full list.

## Architecture: what spans many files

- **The generated world is never stored.** A save holds the seed, `Generator_Version`, clock, climate, camera, the edits, live water and the colony. Changing anything that alters generated output (terrain constants, hydrology, flora, materials) **must bump `Generator_Version`** (`src/castle-worldgen.ads`). Older saves are then refused on purpose. It is now 16 (a tree's trunk goes down through a boulder to the ground, 2026-11-17; 15 was a boulder going into the ground with a skirt round its foot; 14 a fifth of the mountains' boulders, three in ten more on open land, 2026-11-14; 13 was trees reshaped and tall grass in drifts, 12 tarns, 11 wild vegetables in patches, 10 forests and open land, five tree kinds). `./bin/flora_stats` counts what `Castle.Flora` plants on seed 1, the wild vegetables and the tall grass, and draws three thousand trees of each kind alone: it fails if one reaches past `Tree_Reach`, and prints a hash of their shapes that the debug and the release build must agree on.
- **No save compatibility during production** (John, 2026-11-11: "don't worry about ever being compatible about mainting compatibility with old saves during production"). So: change the generator when the look or the game wants it (bump the version, regenerate the eight reference logs in that commit, re-measure whatever the documents quote from a run); when a save's layout or the colony blob changes, bump its version and refuse older ones. Write no new old-version loader and keep no new `tools/colony_vNN.bin`. The loaders and the eight kept blobs that exist (`tools/colony_v7.bin` and `colony_v10.bin` to `colony_v16.bin`, each read by `colony_check`) stay while `colony_check` passes with them; the day one fails because the world or a format moved, delete that check and its blob, and never remake a blob with current code.
- **Pipeline** (`castle-worldgen`): terrain -> geology fields -> hydrology -> deposits -> aquifer field. Only the top 2 m "skin" is generated per 8 m stack. `Castle.Geology.Deep_Brick` produces anything deeper on demand, and `Castle.Chunks.Deepen` lays it open when an edit reaches down.
- **Streaming and draw:** worker tasks (`Castle.Streaming`, `Castle.Jobs`) generate and greedy-mesh stacks nearest first. The main thread uploads them into one quad arena, and `Castle.Render` draws with multi-draw-indirect and vertex pulling. The UI and the figures are drawn the same way, each in one draw call. **Since 2026-11-15 the game holds every stack's blocks and streams the meshes alone** (a stack out of view is asked for without a mesh; Conventions, the first entry).
- **Edits are the one write path.** Player digging, scripted `--dig`, and colony work (paths, picking berries, felling trees from stage 2) all go through `Castle.Edits`. Each edit bumps the generation of its stack (and of its neighbours on a shared edge), then a worker rebuilds the stack and `Castle.World_Blocks` refreshes its packed copy and `Ground_Version`. `Castle.Nav` routes and `Castle.Water` stretches key off those versions to re-plan or re-read (the walking map mends itself from the list of edited columns instead of reading the stack again: Conventions, the first entry). New gameplay that changes blocks should use this path, not poke meshes or blocks directly.
- **The time keys move the clock, not the colony** (`Time_Forward`/`Time_Back`, `Day_Forward`/`Day_Back`: `Game_Clock` is added to and the colony takes no steps for the time passed over). What follows the clock jumps (bedtime, seasons, bushes and vegetables growing back, the deer); what follows the colony's steps does not (hunger, a fire's burning, work). John noticed it (2026-11-11) and decided the same day that they stay as they are: "the scrubbing will reman a debug tool for now". Don't make them march the colony unasked, and don't use them in anything measured.
- **Determinism everywhere.** The colony runs on a fixed clock: `Castle.Colony.Tick_Hz` = 20, with the frame time clamped and multiplied by the speed. Water uses integer depths with a ledger (`Total + Went_Out - Came_In` is invariant). Climate is a pure function of the seed and the clock, plus a little snow/ice/wet state. The checks assert that save -> load -> save gives the same bytes and that a run continues identically after a load. Keep it that way. The sky clock, colony and serfs all advance by the same step.
- **A model is boxes, drawn rounded** (2026-11-11). `Castle.Bodies.Box` has `Round` (the radius its edges are rounded by; by a rule unless set) and `Taper`; the renderer draws every box of every look as six faces of nine cells (`Box_Face_Source` in `castle-render.adb`, shared by the figure shader and the caster's, 324 vertices a box: change both draw counts together, `Castle.Figures.Box_Vertices`). A new model is boxes with those two where the rule does not suit, never a mesh of its own. **What a serf carries is a prop placed from its solved frames** (`Castle.Serfs.Show_Tool`: the axe, the bow; the shoulder log and the carried deer in the game), not a box of its body: a box is baked to one bone, so it cannot go from the hip to the hand. A prop whose pieces must move against each other hangs them on bones of their own (the bow: `Castle.Props.Put_Bow`).
- **Deer reuse the serf machinery:** `Castle.Deer` hangs boxes on the same fifteen `Bone`s (pelvis = hindquarters, chest = forequarters, head = neck+head, arms = forelegs, legs = hind legs) with its own pose solver (the two halves are two boxes on two bones: whoever places the hips and the withers keeps them a back's length apart, `Castle.Animals.Whole_Back`, 2026-11-22); `Castle.Animals` is the four-legged stepper (gait-phase locked) and draws through `Castle.Figures` after `Castle.Serfs.Submit`. One look per class and coat (texture layers are shared, 256 in all). Skins are packed by `Castle.Bodies.Pack_Nets`.
- **Herds** (`Castle.Herds`; to come apart from the stake and populate the whole map when the ecosystem is built, John's word of 2026-11-14: the herds-search entry under Conventions) are stepped by `Castle.Colony.Advance` and saved inside the colony blob (v5; the herds' own blob is its version 2 since colony blob 17). Designer's rule: each herd has a node that plans the route and travel direction; deer wander round it; a threat (someone near, an arrow) makes the node flee, and the deer flee with it and settle round it where it stops (since 2026-11-11; before that they scattered and came back: `Set_Scatter`). Only the node uses `Castle.Nav.Plan`; deer step over nav floors locally, and one left behind takes the way the node planned.
- **The colony's body is split into subunits.** `src/castle-colony.adb` holds the state, the small helpers and a stub (`is separate`) for each larger subprogram, under the same section banners as before: read it as the index. Each larger subprogram is its own file, `src/castle-colony-<name>.adb` (`separate (Castle.Colony)`); a member's step is `Step_Member` plus one procedure per group of states (`Step_Needs`, `Step_Camp`, `Step_Gather`, `Step_Wood`, `Step_Fetch`, `Step_Hunt`). A subunit sees only what is declared above its stub, so new state and helpers go above the stubs that use them. Tunables and capacities are in the spec, never in the body or a subunit.
- **Colony decides, serfs show.** `Castle.Colony` owns the band, jobs, reservations, routes, stockpiles and bushes, and saves them in its own versioned blob. `Castle.Serfs` only presents it: a stepper and second-order filters (`Castle.Second_Order`) over the targets the colony sets. Looks come from `Castle.Bodies` (a genome and an outfit build a rig and a skin), poses from `Castle.Poses` (two-bone IK), and the GPU side from `Castle.Figures`.
- **Colony ground stays loaded.** Stacks within the colony's reach of the homestake are never unloaded, and the colony doesn't advance until all of them are loaded (`Colony_Ground_Ready`). The reach is the colony's to say (`Castle.Colony.Ground_Reach_M`): its work radius as a rule (the 88 m the game has always kept), wider while the band looks further afield or has a path to lay further out. A host must have that ground in before every `Advance` (the game gates on it; `colony_run` brings it in): the colony trusts it (`Ground_In`), and reads the world only on ground that is in. **And only on its own ground** (since 2026-11-15, the whole map being held: `Castle.Colony.Set_Ground_Stacks`, the stacks within the reach in stacks and five more of the stake's, in the game and in the runner alike; Conventions, the first entry).
- **Saves** (`Castle.Saves`): little-endian, written to `PATH.tmp` then renamed, with an FNV-1a trailer. The current format is 6 (the level source water rests at, and which columns have been dug or built in). If you change the layout, bump the format and update the format description in `docs/systems/edits_and_saves.md`; by John's rule of 2026-11-11 (above) nothing new is written to keep an older format readable (the readers that exist stay while they work).
- **Two interfaces, one widget layer** (designer's rules, 2026-11-09; framework, "The player's interface"). Today's panels are the development interface: dense, complete, for building the game. The player's interface will be tooltips and context menus on what his character sees and is near, on foot in third or first person, with a view from above only for staking, zoning, pathing and blueprinting; reports come later, at a desk. Build new dev panels as data views that a tooltip or report can reuse, route every action through a `Castle.Colony` call both interfaces share, pick by a ray (a cursor now, a reticle later), and never add a modal dialog or an alert. Information belongs to things in the world and a zone aggregates what is inside it (no report on what nobody tends). The player and the serfs are one kind of actor using one set of actions, narrowed by role and permissions; delegation runs only downward. Don't write an action only the player, or only a serf, can ever use.
- **The scaffold of stage 5a is how every later interface is made** (2026-11-10). An action: a row in `Castle.Actions` (what it is done to, the lowest rank that may), carried out only through `Castle.Actions.Perform (Order)`; the panels, the context menus, the game's clicks and `Castle.Scenario` all build orders, and none calls a `Castle.Colony` setter (done-test: `grep` for `Set_Job`, `Zone_`, `Lay_Path`, `Place_Stake`, `Set_Reserve` ... in `game/`, `castle-hud.adb`, `castle-scenario.adb` finds only orders). A menu: `Castle.Actions.Menu_For (actor, thing)`. Something to look at: a sheet in `Castle.Views` (rows marked `Known` when the player's character could know them), shown by the tooltip and the tabs through one routine in the HUD; add a line to the sheet, never to a panel. Pointing: `Castle.Pick.Look` on a ray walked by `Castle.Rays`. A new kind of marked ground: a `Zone_Kind` on the zone record, with what it gathers in `Zone_At`, its lot laid out by `Plan_Lot` and what is built on it a row of `Build_Takes` (or, as housing's is, counted from blueprints and asked as the zone's `Once` rows). Who gave a job is that member's director (`Set_Job (I, J, By)`): no one, for the unassigned and for a job taken up on its own.
- **The interface's scale** is a whole number from the window's height unless set (`--uiscale 2.5`; F10 and F11 step it by a quarter; `Castle.Settings` remembers it in `saves/settings.txt`, which a scripted run does not read unless given `--settings FILE`). Lay everything out through `Pix (N)` (N pixels at scale 1, as whole screen pixels) and `Hair` (a rim or a rule), never `N * Sf`: at a scale between whole numbers that keeps every box on the pixel grid, and at a whole scale it must emit the very quads it always did (the proof used was a hash of every quad `ui_check` lays out, before and after). Fit a row or a text by its width at scale 1 (`Inner_U`, `Fits`), so layouts break the same at every scale.
- **UI** (`Castle.UI`, `Castle.HUD`) is immediate mode. Tabs, scroll lists, tooltips and popups keep no state of their own: which tab, how far scrolled and whether a menu is open are the caller's (`Castle.HUD.Tool_State`, the HUD's menu). A popup is laid out last and what is under it gets no clicks; a tooltip is not in `Wants_Mouse`. Panel rects from the last frame decide `Wants_Mouse`, so clicks on panels never reach the world. Key bindings are one table in `Castle.Input.Bindings`. The font glyphs are pictures in `tools/font_glyphs.py`, which generates `src/castle-font_data.ads`. Edit the script and regenerate; don't hand-edit the `.ads`.

The rules of every change, a line each (the files above and the sections before this one have them whole):

- **Nothing is merged without John's explicit word.** Praise is not that word. New work is on a new branch from `main`, a commit a rule, each rule behind a switch that gives the game as it was.
- **The gate before any report: `tools/gate.sh`** (from a clean copy of the commit, three quarters of an hour, started in the background).
- **A change that is not about the game's behaviour leaves the eight reference logs and the log of the game as it is played (`tools/today_check.sh`) line for line with none recorded again**, and the gate's states as they were.
- **Say of the build only what a run showed**; a count goes with what the run could and could not have shown.
